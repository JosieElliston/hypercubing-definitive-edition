# Hypercubing Definitive Edition: notes

The goal is one Mac bundle, plus a Linux edition (see "Linux edition"), of the
important hypercubing programs for a few people in the community. It should use as little storage as possible and need little
upkeep. This is not a public release, so redistribution licensing is not a gate.

## Layout

- `build.sh`: builds both editions, on the Mac: `dist/mac/hypercubing/` (`./build.sh install`
  copies it into `/Applications/hypercubing/`) and `dist/linux/hypercubing/`;
  `./build.sh package` makes the zip and tarball. Its header lists the commands. Pinned
  versions and download URLs live in it. Downloads are cached in `cache/`.
- How `build.sh` is organized: each program's `payload_<program>` function writes a payload
  (files plus a manifest) into `build/any/`, and `package_mac`/`package_linux` turn payloads
  into each edition. Programs built differently per edition (including the native Rust programs)
  have `payload_<program>_mac` and `_linux` instead. The comment above `new_payload`
  defines the payload format. Why this shape? Both editions then ship byte-identical Windows
  exes and jars from one build, and neither edition is derived from the other's output. An
  earlier Linux build unpacked the Mac zip, had to undo Mac packaging (paths, `.icns` icons,
  JogAmp natives, pins repeated by hand), and picked up `._` AppleDouble files from the zip,
  which crashed Magic120Cell (it loads every `*.settings` in its folder).
- `lib/`: the Mac launchers (`mac-{wine,java,native}-launcher.sh`, one per app kind), the
  Linux launcher and menu installer (`linux-launch.sh`, `linux-install.sh`), plus
  `exe2ico.py` (pulls the icon out of a Windows exe) and `geraniumspot_main.py` (Geraniums
  Pot's PyInstaller entry point). Every launcher sources the payload's manifest as its config.
- `lib/README-mac.md` and `lib/README-linux.md`: the readmes that ship at the top of the
  distributed folders, written for the recipients. When you add, drop or re-version a
  program in `build.sh`, update both program lists, sizes and credits too.
- Icons: `lbicon <ABBR>` fetches the leaderboard's SVG from
  `https://assets.hypercubing.xyz/img/icons/programs/<ABBR>.svg` (as of
  2026-11-22, those exist for HSC1, HSC2, MC4D, MC5D, MC7D, MPU, MT, MZRG, CG, FHC,
  AKS and M120C; MC3D and NM11C are just a generic Java cup). Otherwise a Windows
  app uses its exe's icon. Our own icons for
  MC3D, Eleven Cell, ElevenCell3D, and Laminated are in `icons/`, generated by
  `scripts/own-icons.py`. Edit the script, not the SVGs. `scripts/icon-grid.py` draws `icons/grid.png`,
  the root README's picture of every app; rerun it after a build that adds, drops or
  re-icons a program. `iconr <app> <out.png> <px>`
  renders an app's icon the way macOS 26 shows it in Finder, including the squircle
  it puts non-square icons in and its glass highlights. The Dock can look different.
  Render a fresh copy of the app: right after a rebuild, the `dist/` path can still
  return the blank generic icon. Icons are rendered with `lib/icon2png.py` (Pillow) and
  `rsvg-convert`, both build dependencies. Why not sips? It converts 4-bit .ico
  files with alpha 15 instead of 255, which made the icons nearly invisible.
- Windows apps set `LSUIElement` because the launcher process never becomes a GUI
  app; without it, the Dock shows a second icon that bounces until it times out.
  The Dock entry is Wine's process, named after the exe (e.g. `MS5D.exe`).
- `VERSION`: the bundle's version (see "Versioning"). `CHANGES.md`: what each version changed,
  written for the recipients.
- `checkouts/`: clones of the programs' source (gitignored; each is its own repo).
- `patches/`: our changes to upstream sources, which `build.sh` applies to fresh clones. The
  program's section says how each patch is kept in sync with its checkout.
- `shim/`: the Managed DirectX shim (see "MDX shim" below).
- `scripts/`: helper scripts. Build the window listers with `swiftc -O scripts/<name>.swift -o scripts/<name>`.
  `wlany <owner substring>` lists windows on every Space. `wl`/`wlall` only see the
  current Space, so they miss windows opened while the user is in another
  (full-screen) Space. That caused the 20–170 s "window visible" timing outliers.

## Mac runtime layout (installed)

- `/Applications/hypercubing/Support/engine`: the Wine engine (Sikarugir WineCX
  24.0.7_7 plus Template 1.0.27's dylibs; gecko, GStreamer and the DXVK/D3DMetal
  renderers are stripped). About 490 MB. `Support/jre`: a jlinked Java 25
  runtime, about 51 MB.
- `~/Library/Application Support/Hypercubing/`: per-user state.
  - `prefix/` is the one Wine prefix. The first launch of any Windows app creates
    it with `wineboot -u`, which takes about 30 s. Its Windows user is always
    `crossover` (CX engines force it); Desktop, Documents and Downloads link to
    the Mac folders.
  - `logs/<app>.log` holds each app's stdout/stderr.
  - `<app>/` is the working directory for Java and native apps.
- Each Windows app carries its files in `Contents/Resources/program/`. The launcher
  rsyncs them to `C:\Program Files\<name>` when `Contents/Resources/stamp`
  changes, without `--delete`, so settings and saves survive upgrades.
  If a program saves settings into a file it also ships (MPU's
  `MPUlt_settings.txt`), list it in `KEEP=(...)` in its manifest
  (see `payload_mpu`), or upgrades reset it. The Linux edition uses `KEEP` too (see "Linux edition").

## Decisions

- **One Wine engine, one wine-mono prefix, one JRE, plus native apps.** The engine
  plus its Frameworks is about 1.2 GB, so having one copy per app is what wastes
  space.
- **Do not add a Microsoft .NET prefix.** Why? It is about 1.1 GB. Its installers
  also misbehave in this engine: `winetricks dotnet48` spawned about 20 conhost.exe
  processes spinning at about 460% CPU and then rolled back (2026-11-22).
- **Target .NET Framework 4.8 (net48), AnyCPU, no Prefer32Bit.** Why? net48 is the
  final .NET Framework, and wine-mono implements it with no extra runtime. Modern
  .NET would need Microsoft's desktop runtime installed into Wine and gains nothing
  on Mac, since WinForms is still Windows-only. Keep projects SDK-style so changing
  the TFM stays a one-line change.
- **Never ship 32-bit managed exes.** Why? Under this engine, x86 processes run in
  Wine's "experimental wow64 mode", where OpenGL calls are thunked and very slow.
  That is what made MagicTile slow. `scripts/corflags.py <exe> anycpu` clears the
  CLR 32BITREQUIRED/32BITPREFERRED flags on a prebuilt exe.
- **The prefix must not stay running in the background.** This is the user's
  preference. A shared running wineserver would save about 3.5 s per launch, and
  that is the only real startup win we found.
- **Magic Cube 5D and Magic120Cell are source-ported, not shimmed** (2026-11-22).
  Both were C++/CLI mixed-mode exes, which wine-mono can't load, and a Microsoft .NET
  prefix is ruled out (above). The C++/CLI was confined to the glue, so the port is
  small and kept upstreamable; see "Roice's C++/CLI ports" below.

## Wine engine facts (Sikarugir wrapper, WineCX 24.0.7 = "wine-9.0 KegworksCX")

- Running the wrapper's wine directly needs
  `DYLD_FALLBACK_LIBRARY_PATH=$C/Frameworks:/usr/lib WINEPREFIX=$C/SharedSupport/prefix`,
  or it fails to load `@rpath/libinotify.0.dylib`. SIP strips `DYLD_*` when a
  `/bin/sh` script such as winetricks runs, so for winetricks, symlink
  `Contents/Frameworks/*.dylib` into `Contents/SharedSupport/` instead.
- There is no `wineboot` binary. Use `wine wineboot -u`.
- Before copying a prefix, `chmod -R u+rwX` it, because some files are unreadable
  (e.g. `PCHEALTH/ERRORREP/QSIGNOFF`). Use `cp -cR` so APFS clones share blocks.
- Sikarugir's launcher sometimes quits about 0.5 s after `open`. It happened on
  the first open from /tmp, when opening two apps at once, and after a plist edit
  or `wineserver -k`. Retrying worked. The root cause was not isolated.
- Startup breakdown (2026-11-22, MagicTile run directly, about 6.4 s to window;
  MC7D-KB about 6.2 s):
  - about 1 s: Wine boot
  - about 2.4 s idle: the app's wait for explorer.exe to report input-idle. It
    ends on explorer's 2 s clipboard timer and is unchanged with esync/msync off.
  - about 1.2 s: Mono plus WinForms load
  - the rest: app init
  Launching through Sikarugir adds about 2 s.

## Managed DirectX findings (2026-11-22)

- **wine-mono 9.0.0 ships its own partial Managed DirectX in its GAC.** It has
  Microsoft.DirectX and .Direct3D 1.0.2902.0 with Microsoft's token, Direct3DX
  only at 2.0.0.0, and no Mesh. Unmodified MC7D crashes on it with
  `InvalidProgramException`. Because the GAC wins over the app folder, a shim at
  the *same* version next to the exe is ignored.
- **A drop-in shim works** if it is built at a new version (1.0.2911.0),
  public-signed with Microsoft's public key (`experiments/mdx-shim/key/`), and
  paired with a `bindingRedirect` from 1.0.2902.0 in `<exe>.exe.config`. Limits:
  the shim must match the exact signatures of every member used, and the exes stay
  32-bit unless flag-patched (see below). The user chose the shim for all four
  programs and no ports (2026-11-22). Why? Unmodified upstream binaries, including
  new MC7D-KB releases, drop straight in, and there are no forks to maintain.
- **SharpDX 4.x has no D3DX9.** The MC7D-KB port replaced it with its own
  `s3d/MdxMath.cs` (Matrix/Vector3/Quaternion, cross-checked against
  SharpDX.Mathematics) and `s3d/MdxMesh.cs` (Box/Cylinder/Sphere). The shim reuses
  both and does not use SharpDX.
- Startup to window: the original (MS .NET 3.5) cold-starts in 5.6 s. The net48
  port on wine-mono takes 6.1 s cold and about 5.0 s warm. A self-contained net8
  build takes 5.0 s cold but is 162 MB, versus 0.8 MB for net48.

- The original exes (mc7d.exe v0.8.4, m3dht633.exe) are ILONLY with
  32BITREQUIRED set. The x86 requirement exists only because the real MDX is
  32-bit native code. With the pure-managed shim, `scripts/corflags.py <exe> anycpu`
  lets all four run 64-bit (verified 2026-11-22 21:40 EST).
  32-bit is not necessarily slow for these programs: original MC7D ran fine in
  wow64. The wow64 slowness hit MagicTile because of per-vertex immediate-mode GL
  calls.
- The net8 self-contained MC7D-KB port crashes ("Program Error" dialog) when the
  File menu is clicked. net48 does not. Not investigated.

## MDX shim (`shim/`)

A drop-in replacement for the parts of Managed DirectX 1.1 that MC7D-KB, MPUlt,
Magic Simplex 5D and Magic Hyperbolic Tile use. Three SDK-style projects (net48,
AnyCPU) build `Microsoft.DirectX`, `.Direct3D` and `.Direct3DX` (about 75 KB together).
Direct3D calls go straight to `d3d9.dll` (Wine's wined3d) through COM vtable slots with
C# function pointers, so there is no SharpDX and no d3dx9. `Mesh` is built on plain
vertex and index buffers.

How it loads (each step is required):
- version 1.0.2911.0, public-signed with Microsoft's key (`shim/key/ms-public.snk`),
  so the exes' token `31bf3856ad364e35` matches;
- `<exe>.exe.config` redirects 1.0.2902.0 to 1.0.2911.0, written by
  `scripts/mdx-config.py`. Why? wine-mono's GAC has a broken partial MDX at 1.0.2902.0
  and wins over app-local DLLs. `<configuration>` itself must stay un-namespaced: a
  first version written with ElementTree put the asm.v1 xmlns on it, the runtime
  silently ignored the redirect, and MC7D-KB died with the GAC MDX's
  InvalidProgramException.

Constraints that will bite:
- **Signatures must match exactly, modifiers included.** Mono binds a member reference
  only to a method with the same custom modifiers. `CustomVertex.*.StrideSize` returns
  `int modopt(IsConstModifier)` in the C++/CLI original; C# can't emit that, so
  `shim/tools/AddModOpt` (Mono.Cecil) rewrites return types marked
  `[return: ReturnModOpt(...)]` after compiling. To check a new program or a new
  release, diff what it references against what the shim defines; any line printed is a
  missing member:
  `comm -23 <(mdx-surface --sig <exes>) <(mdx-surface --defs <shim dlls>)`
  (`experiments/mdx-surface`). As of 2026-11-22 21:40 EST it prints nothing for the
  four exes.
- Only the members the four programs reference are implemented, plus a few trivial
  neighbors. `experiments/mdx-dump` prints the real assemblies' types, enum values and
  layouts (from `experiments/mdx-shim/ref/`); `experiments/ildump` prints the IL of
  methods that use a given member, which stands in for source for m3dht633.exe.
- Deliberate differences from real MDX: `Pool.Default` buffers are created in the
  managed pool, so `Reset` never fails on them; after every `Reset` the render states,
  transforms, material and lights set through the shim are applied again (not the
  viewport); `SupportedDisplayModes` lists at most 64 X8R8G8B8 modes, because the
  programs' sample framework copies them into a fixed `DisplayMode[100]`;
  `Mesh.Box/Cylinder/Sphere` have D3DX's layout but not its exact vertices.
- `VertexBuffer.Lock` returns a managed array that the shim keeps as a mirror of the
  buffer; `Unlock` uploads it. A vertex type with non-blittable fields would fail to pin.
- Debugging: `MDXSHIM_LOG=1` logs device creation, resets and failed HRESULTs (with
  stack) to stderr, i.e. the app's log. `MDXSHIM_DUMP=<dir>` writes the back buffer to
  `<dir>/<exe name>.bmp` on every Present (Unix paths are mapped to `Z:`), which is how
  rendering was verified without Screen Recording permission.
- **Wine's Mac driver draws a D3D child window above all its siblings, ignoring
  z-order.** wine-mono's dock layout also gives Fill-docked controls the whole parent
  area. Together, in MPUlt, Magic Simplex 5D and Magic Hyperbolic Tile the 3D view hid
  the menu strip (and in MPUlt the bottom button row), so they looked like they had no
  menus (2026-11-22). `FillFix.cs` re-lays out the render control and its Fill-docked
  ancestors to the space left by docked siblings. `MDXSHIM_NOFILLFIX=1` turns it off,
  and `MDXSHIM_LOG=1` logs each fix. MC7D-KB uses a classic `MainMenu` (non-client),
  so it was unaffected.
- MPUlt rewrites `MPUlt_settings.txt` itself, so it's in KEEP (see "Mac runtime layout").
  It only reads `MPUlt_puzzles.txt`, which the build extends with the
  hypercubing.xyz page's definitions (`scripts/mpu-merge-puzzles.py`; multi-word
  names get underscores, because MPU cuts the name at the first space). That file is
  overwritten on update, so puzzles a user adds there are lost.

## Linux edition

`./build.sh linux` builds `dist/linux/hypercubing` (on the Mac, like the Mac edition). One
folder per program, each with `run`, `app.conf` (the manifest) and `icon.png`;
`Support/launch` (`lib/linux-launch.sh`) starts all of them, and `install.sh`
(`lib/linux-install.sh`) writes `.desktop` files into `~/.local/share/applications`.

Decisions (2026-11-23, with the user):
- **Users bring their own Wine; no engine ships.** Why? Linux users span many distros, and
  every distro packages Wine. What makes the Windows programs hard is wine-mono, not the OS:
  the MDX shim, the C++/CLI ports and the 64-bit flag patches are needed on any Wine. So the
  Linux edition ships the same payloads as the Mac one.
- **Everything is written inside the extracted folder**: the Wine prefix and logs in
  `Support/`, each program's files next to it. Why? The user's preference, matching the usual
  convention outside macOS (HSC does it too). Programs run straight from their folder (Wine
  maps `/` to `Z:`), so the Mac launcher's stamp/rsync copy into `C:\Program Files` is gone.
  Updating means extracting over the folder, so shipped files a program saves settings into
  (`KEEP` in the manifest, e.g. MPU's `MPUlt_settings.txt`) ship as `<file>.default`, and the
  launcher copies one into place only when the real file is missing.
- **3to4++ and Geraniums Pot run through Wine.** 3to4++ is cross-compiled with MinGW, and
  Geraniums Pot ships upstream's Windows build from the pinned checkout. Version 1.0 used
  Wine for circleguy too, because a build on cif-gpu (Debian 13, glibc 2.41) could require a
  newer glibc than users have. circleguy now cross-compiles from the Mac with Zig for Linux
  x86-64 and glibc 2.28. The build checks the ELF's glibc symbol versions before packaging.
  HSC ships its upstream Linux binaries, with the icon from each version's app resources
  (the repo's `assets/icon-1024.png` has HSC 1's faces in other colors).
- **Native circleguy test (2026-11-23 12:18:48 EST).** A plain `cargo build --locked --release`
  on cif-gpu required glibc 2.39. `./build.sh linux circleguy` produced an ELF whose newest
  glibc symbol version is `GLIBC_2.28`. The packaged `run` opened the app under Xvfb on cif-gpu
  with `WINE=/bin/false`. Pressing `f` turned the puzzle.
- **Flat Hypercube and Laminated (2026-11-23 12:37:21 EST).** Both use the same native Linux
  x86-64/glibc 2.28 build path as circleguy. Flat Hypercube's terminal manifest opens a terminal
  from the app icon and passes no arguments. Invoking the launcher directly preserves the
  terminal and working directory for logs, filters, and preferences. Laminated uses rfd's file
  chooser portal or zenity on Linux.
- Gelatinbrain ships only the JogAmp natives for its edition (the payload's `mac/` and `linux/`
  parts); JogAmp finds them next to its jars.
- The Linux JRE is linked by the Mac's jlink from Temurin's separate **jmods** tarball (the
  Linux JDK tarball has no jmods), at the same build as `$JDK_HOME`. Given no Linux
  `java.base`, jlink silently links the Mac's own modules instead, so the build checks that
  `Support/jre/bin/java` is an x86-64 ELF.

Testing on `ssh cif-gpu` (Debian 13, headless, no sudo; set up 2026-11-23 in
`~/hde-linux-test`):
- Wine: Kron4ek's portable builds in `wine/` (9.0, 10.0 and 11.0 wow64), each with the
  matching wine-mono symlinked into its `share/wine/mono/` (10.0 wants 9.4.0, 11.0 wants
  10.4.1; the version is in `strings -el appwiz.cpl`). X: Xvfb, xdotool, x11-utils and
  Xtigervnc from `apt-get download` + `dpkg-deb -x` into `x/`; `env.sh` sets the paths and
  `xstart` starts Xvfb on `:77`. `run.sh <wine ver> <app folder> <exe> <seconds> [shot.png]`
  runs one program; `e2e.sh` runs every program of an extracted tarball in `e2e/`.
- **Don't screenshot with `xwd -root`.** It returned Wine's windows with colors split into a
  repeating R/G/B pixel cycle and squeezed to 3/4 width, while non-Wine windows came out
  right, and it cost an hour of blaming Wine. Read Xvfb's framebuffer instead
  (`Xvfb -fbdir /tmp/hde-fb`, then `xwd2png.py < /tmp/hde-fb/Xvfb_screen0`), which matches
  a VNC capture. The cause wasn't isolated.
- There's no window manager, so `xdotool windowactivate` doesn't give keyboard focus: use
  `windowfocus --sync`, then click an empty spot. Unlike `poke` on the Mac, xdotool sends real
  input, so drags, held keys and modifiers work. MC7D-KB keybinds are a held key plus a press:
  `xdotool keydown d key i keyup d`.
- Wine's X11 driver doesn't have the Mac driver's z-order bug: menus show without FillFix,
  which stays harmless.

## Versioning

- The bundle is x.y, in `VERSION`. Bump y for any change to a program's pin, or for adding
  or removing a program. Bump x for changes every app shares or that touch users' files: the
  launchers, the Wine engine, the Java runtime, the MDX shim, or the layout under
  `~/Library/Application Support/Hypercubing`. Why x for those? They can break every app at
  once, or people's settings and saves.
- Each release: a line per change in `CHANGES.md`, `./build.sh`, `./build.sh package`, and a git tag `vX.Y`.
- `VERSION` only appears in the shipped READMEs' titles (`@VERSION@` in `lib/README-mac.md` and
  `lib/README-linux.md`) and the zip's and tarball's names. Each Mac app's Get Info version
  (`CFBundleShortVersionString`) is the program's own, from `APP_VERSION` in its payload
  function; apps with no upstream version leave it out. Why not the bundle version? The user
  wanted each program to show its own. Linux has nowhere to show it.
- Pins: every program is pinned in `build.sh` by a version in its URL, a sha256 (for URLs that
  don't change on a new release), or a commit (for checkouts). Why? So two builds of one
  version ship the same programs, and an upstream change shows up as a failed build, not
  silently.

## Building

- Build dependencies besides Xcode's command-line tools: `uv` (Homebrew; it downloads
  the pinned CPython into `cache/uv-python` and the venv into `checkouts/GeraniumsPot-build`),
  `rsvg-convert`, Pillow for `python3`, the .NET SDK (see below), rustup's cargo, cmake, a JDK,
  and `mingw-w64` (Homebrew, for the MC5D and Magic120Cell core DLLs and the Linux edition's
  Windows build). For native Linux Rust builds, put `zig` and `cargo-zigbuild` on `PATH`
  (tested with Zig 0.15.2 and cargo-zigbuild 0.23.4). The build adds rustup's
  `x86_64-unknown-linux-gnu` target itself.
  Laminated ignores its `Cargo.lock` upstream. After changing `laminated-dependencies.patch`,
  regenerate `patches/laminated.Cargo.lock` from the patched source and rebuild both editions.
  The patch updates three-d past the old winit/objc2 stack and updates rfd without adding a
  link-time GTK dependency on Linux.
  The Python and pip pins for Geraniums Pot are `GP_PYTHON`/`GP_PIP` in `build.sh`; changing
  them rebuilds the venv.
- The .NET SDK 11.0.100 is installed user-locally in `~/.dotnet`, so use
  `~/.dotnet/dotnet`. Why user-local? The brew cask needs sudo.
- The MDX shim: `./build.sh` builds it along with the MDX programs, or run
  `~/.dotnet/dotnet build shim/Microsoft.DirectX.Direct3DX -c Release` (it builds the
  other two projects and the AddModOpt tool). The three DLLs land in
  `shim/Microsoft.DirectX.Direct3DX/bin/Release/net48/`.
- `checkouts/mc7d-kb`: run `~/.dotnet/dotnet build rubik7d.csproj -c Release`.
  The output goes to `bin/Release/net48/`.
- `experiments/mc7d-port-test/MC7D-port.command` launches a test build. It points
  at `/tmp/mc7dtest/Test.app`, which won't survive a reboot. To recreate it,
  `cp -cR` MagicTile.app there, then copy the build into
  `drive_c/Program Files/MC7D-KB-port/`.
- `experiments/mc7d-port-test/instrumentation.patch` and `TestDump.cs` dump the
  D3D back buffer and pick results for the port. For the shim use `MDXSHIM_DUMP`.
- `experiments/mc7d-port-test/poke` posts clicks, keys, resizes and close to a window
  picked by `POKE_TITLE` (title prefix) and `POKE_SIZE` (the 3D view's client size);
  with no match it lists the visible window titles. Run it with the same `WINEPREFIX`
  as the app.
- Wine refuses to create a prefix directly in `/tmp` ("not owned by you"); use a
  subdirectory such as `/tmp/shimtest-w/prefix`.

## Roice's C++/CLI ports (Magic Cube 5D, Magic120Cell)

The port lives on branch `hde-port` in `checkouts/MagicCube5D` and `checkouts/Magic120Cell`
(one commit on upstream master, not pushed) and as `patches/<repo>-hde-port.patch`, which
`build.sh` applies to a fresh clone. What it changes: the C++ core builds as a plain DLL
(`MagicCube5DCore.dll` / `Magic120CellCore.dll`) with a C API in `coreApi.cpp`; the
`cubeFrame` glue and the entry point moved to `CubeFrame.cs`/`Program.cs` in the C# GUI,
which is now the exe (SDK-style csproj, net48, AnyCPU); the loaders use C stdio instead of
System::IO; a few MSVC-only constructs were made portable. The vcxproj files were converted
to native DLL projects with an x64 platform so the branch can go upstream, but MSVC builds
of them are untested.

- **Edit the branch, then regenerate the patch**: `git -C checkouts/<repo> diff --binary
  master hde-port > patches/<repo>-hde-port.patch`. Why? `build.sh` uses an existing
  `hde-port` branch as is and only applies the patch when the branch is missing, so a stale
  patch goes unnoticed until someone builds from scratch. It never pulls upstream, because
  the patch might not apply to a newer upstream.
- **The log formats are byte-compatible**: CRLF lines, as .NET's StreamWriter wrote them;
  reading accepts CRLF, LF and a UTF-8 BOM. Verified 2026-11-23 01:50 EST: Magic120Cell's
  shipped `full_scramble.log` (written by the original program) loads and saves back
  identical, and MC5D logs and macros round-trip.
- Magic120Cell's sources must be compiled per directory with the vcxproj file lists (see
  `payload_m120c`). Why? geometryLib has a stale root `glInit.cpp` besides `gl/glInit.cpp`,
  basenames repeat across the two trees, and each tree's `#include <stdafx.h>` must find
  its own stdafx.h.
- Magic120Cell's window icon moved from `MainFrame.resx` to an embedded `.ico`. Why? The
  dotnet SDK only compiles non-string resx resources with System.Resources.Extensions,
  which would have to ship with the exe.
- Neither program's GL view overlaps its menu strip (window tree, 2026-11-23), so they need
  no FillFix-style workaround.
- Testing without Screen Recording permission: add a temporary `glReadPixels` back-buffer
  dump in `CubeFrame.DoRender` (not in the patch). `poke` can click and close, but posted
  messages can't carry real button or modifier state: WinForms reports `MouseButtons.None`
  on posted drags, and Ctrl shortcuts don't fire. So drags, Ctrl/Shift clicks and menu
  shortcuts need a real mouse.

## Geraniums Pot

Built from upstream's `Source/` (unmodified) by PyInstaller, through our entry point
`lib/geraniumspot_main.py`. Its docstring lists the debug hooks: `GP_DEBUG_SHOT` saves the
window to a png, `GP_DEBUG_EVENTS` injects clicks, keys, file drops and a dialog cancel. That is
how it was tested without Screen Recording or Accessibility permission.

Constraints that will bite:
- **Tk must start before pygame.** If SDL creates the NSApplication first, Tk 8.6.11+ aborts
  in its first color lookup (`-[SDLApplication macOSVersion]: unrecognized selector`). The
  entry point creates a withdrawn Tk root first; SDL then adopts Tk's NSApp. Upstream's own
  `Tk().withdraw()` comes after `pygame.init()`, so a plain freeze of main.py crashes on start.
- **Upstream's `glob.py` (its global settings) shadows the stdlib `glob`.** PyInstaller bundles
  the stdlib one regardless of `--paths`, and the app dies with `module 'glob' has no attribute
  'BORDER'`. The build ships upstream's file as `gp-glob.py` and the entry point loads it as `glob`.
- **A plain onedir build can't live in `Contents/MacOS`:** its bootloader then looks for
  libpython in `../Frameworks`. So the build uses `--windowed` and merges PyInstaller's
  MacOS/Frameworks/Resources into our bundle.
- pygame 2.6.1 has wheels only up to CPython 3.13 (as of 2026-11-22), hence Python 3.13.
- Files: it reads `Garden/`, `fonts/arialn.ttf`, `Photo/` and its png from the working directory
  and writes F7 screenshots there. `fonts/arialn.ttf` (arrow markers) exists only in the Windows
  build, so `build.sh` pulls it out of the repo's `Unpacked App/*.7z` with `/usr/bin/bsdtar`.
  `Photo/` (about 12 MB) stays in the bundle, and the entry point symlinks it into the working
  directory on each launch. Upstream writes its ini (last opened puzzle) to
  `$HOME/Geraniums Pot <version>/` on non-Windows; the entry point redirects that to the
  working directory. Saves and move files go wherever the user picks in the save dialog.
- F11/F12 with the built-in first puzzle (no file loaded yet) open the file dialog. That is
  upstream behavior, not a hang.
- **The macOS window surface has an alpha channel** (ARGB8888; on Windows it has none), and
  upstream leaves alpha 0 in it wherever a marker's transparent pixels were drawn. During
  animations pygame alpha-blits the ring sprites onto the window, and over alpha-0 pixels it copies
  the source pixel outright, so transparent sprite pixels turned black: black boxes on markers
  (seen on "Gear Mandorla"). The entry point sets the window's alpha to 255 before every
  `pygame.display.update()`. This also makes `GP_DEBUG_SHOT` pngs come out right.
